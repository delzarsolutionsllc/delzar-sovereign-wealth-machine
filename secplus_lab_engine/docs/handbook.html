1. How to use this document

This handbook describes everything built so far: the purpose, the architecture, each lab's engine and decision rules, data formats, configuration, tests, and how to add more. Every function signature, file name and sample result was taken from the code as it stands, not written from memory.

If you are an AI reading this The project is a modular Python CLI. Every lab follows the same module contract (Section 3.3). To extend it, follow that contract, keep to the standard library, load all policy from config/default_policies.json and scenarios from data/*.json, add pytest tests, and register the lab in labs/__init__.py. Section 18 has recipes and a full lab skeleton. Section 20 is a ready-made prompt.
If you are the learner Read Sections 2–4 first, then one lab section at a time. Run that lab (python main.py lab N), then quiz yourself (python main.py challenge N) before reading its "Decision logic" table.

2. Purpose & learning philosophy

Goal: master the manual security operations behind CompTIA Security+ SY0-701 before designing automated AI agents that perform them. Each lab simulates one operational domain realistically enough to show:

  1. How the control works: the actual decision logic, not just definitions.
  2. Where manual processes fail: privilege creep, untested rollback plans, evidence destroyed by pulling the plug.
  3. How an AI agent should be governed in that same domain: least privilege, human-in-the-loop, audit trails.

Every lab ends with an "Exam & Architectural Insight" panel with five parts: the SY0-701 objective, key concepts, manual failure modes, AI-governance guidance and exam tips.

The arc of the project: Labs 1–4 and 6–7 teach individual controls. Lab 5 shows how to put guardrails on automation. Lab 8 wires them all together into the architecture the learner is building toward: detect → AI agent proposes → governor decides → human approves → the owning control executes.

3.2 Design principles

  • Offline and standard-library only. No network, no API keys. rich is optional; UI(plain=True) renders ASCII.
  • Policy as data. Thresholds, roles, weights, inventories and guardrails live in config/default_policies.json; scenarios live in data/. Logic lives in Python. Changing JSON changes outcomes, and challenge answers follow automatically.
  • Pure engines, thin demos. Each lab has testable engine classes and functions (no printing) plus a run_demo() that renders through the UI facade.
  • Deny by default, explain everything. Every decision returns its reasons (strings), which feed the tables, challenge explanations and tests.
  • Tamper evidence. Audit trails (log manifests, governor ledger, custody ledger) use salted SHA-256 hash chains and HMAC.
  • Deterministic. Injectable clocks and seeds make results reproducible for tests and quizzes.

5. Lab 1 — Joiner/Mover/Leaver & Access Governance

4.6 IAM5.1 SoD2.4 privilege creep File: labs/lab1_jml_governance.py · Data: sample_identities.json

What it simulates

A miniature Identity Governance & Administration (IGA) platform driven by an HR feed. Joiners get birthright access from their role. Movers should lose their old role's permissions; leaving them in place shows privilege creep. Leavers are disabled, fully revoked and get a deprovisioning ticket. Every access request passes a status gate, then RBAC, then ABAC.

Engine API

class IdentityGovernance(policy: dict, clock=None)
  joiner(record) -> Identity                 # validates fields, role and clearance; provisions role perms
  mover(user_id, new_role, new_department=None, revoke_previous=True) -> dict
                                             # revoke_previous=False simulates creep: old role becomes an extra role
  grant_extra_role(user_id, role)            # ad-hoc "temporary" grant (creep source)
  leaver(user_id, reason) -> DeprovisionTicket
  suspend(user_id, reason)                   # IR use: disable but KEEP entitlements (used by Lab 8)
  check_rbac(user_id, permission) -> bool
  check_abac(user_id, resource, hour) -> (bool, reasons)
  evaluate_access(user_id, action, resource, hour=12) -> AccessDecision   # gate: STATUS | RBAC | ABAC | ALLOW
  detect_sod(user_id=None) -> list[SoDConflict]
  access_review() -> list[dict]              # orphaned access, privilege creep
Dataclasses: Identity, AccessDecision, SoDConflict, DeprovisionTicket

Decision logic

RuleBehaviour
Status gateOnly allowed_employment_status (default active) may access anything
RBACPermission must be in the union of the user's role permissions
ABAC: clearanceclearance level ≥ resource classification level (public 0 → secret 3)
ABAC: departmentFor confidential/secret data, user department must equal the data owner's
ABAC: timesecret data only inside business hours (07–19)
SoDFlags a user holding both permissions of any sod_conflicts pair (e.g. po:create + po:approve)
Leaver SLAReason containing "cause" → priority P1, due in 1 hour, "cut access BEFORE notification"; otherwise P3, due in leaver_sla_hours (24)

Data format (sample_identities.json)

{ "events": [
    {"type":"joiner","identity":{"user_id","name","department","role","clearance","manager"}},
    {"type":"mover","user_id","new_role","new_department","revoke_previous":false,"note"},
    {"type":"grant","user_id","extra_role","note"},
    {"type":"leaver","user_id","reason","last_day"} ],
  "access_checks": [ {"user_id","action","resource":{"name","classification","department"},"hour"} ] }

Sample outcome

5 identities · 4 SoD conflicts (SOD-01 PO create+approve, SOD-02 ghost vendor, SOD-03 code→prod, SOD-04 admin audits self) · 2 deprovisioning tickets (one P1) · 3 of 5 access checks denied · 3 privilege-creep review findings. Challenge mode: 12 questions (which SoD rule, ticket priority, ALLOW/DENY).

6. Lab 2 — Zero Trust Access Evaluator (PE / PA / PEP)

1.2 Zero Trust4.6 conditional access File: labs/lab2_zero_trust_evaluator.py · Data: sample_access_requests.json

What it simulates

The NIST SP 800-207 model. In the control plane, the Policy Engine (PE) scores each request and the Policy Administrator (PA) issues or revokes short-lived signed tokens. In the data plane, the Policy Enforcement Point (PEP) checks every request before it reaches the resource.

Engine API

class PolicyEngine(policy).evaluate(req: AccessRequest) -> PolicyDecision(verdict, trust_score, required_score, reasons)
class PolicyAdministrator(signing_key, ttl_seconds, clock)
  issue(req, decision, ttl=None) -> token | None      # only for ALLOW
  revoke(token) · revoke_subject(subject) -> count · verify(token) -> (ok, reason, claims)
  decode_unverified(token) -> claims                   # token = base64url(canonical JSON claims) + "." + HMAC-SHA256
class PolicyEnforcementPoint(admin, resources).handle(token, resource, action="read") -> EnforcementResult
class ZeroTrustGateway(policy, clock)                  # wires PE + PA + PEP
  request_access(req) -> (decision, token|None)
  complete_step_up(req, decision, mfa_passed) -> (final_decision, token|None)
Token claims: jti, sub, scope (one resource), act (one action), dev, iat, exp

Trust algorithm (score starts at 100)

SignalPenaltySignalPenalty
IP reputation bad−40 and always DENYNo MFA−25
IP reputation suspicious−15User risk high (UEBA)−30
Device health < 70−30Geo ≠ usual geo−20
Device unmanaged−20Outside 07–19−10

Checked first: an unknown resource → DENY; subject not entitled to the resource → DENY. Then: bad IP → DENY. If the resource requires MFA and none is presented → STEP_UP if score ≥ 50, else DENY. Score ≥ the resource's min_score → ALLOW; ≥ 50 → STEP_UP; otherwise DENY.

Step-up (adaptive identity): a failed MFA gives DENY and flags the subject as risky. A passed MFA re-evaluates with MFA present and adds 15. If that reaches the requirement, the result is ALLOW with a token TTL of 900/3 = 300 s; otherwise DENY. MFA proves who is asking but cannot repair an unhealthy device.

PEP checks, in order: no token → malformed → HMAC signature → revoked → expired → scope ≠ resource → action mismatch.

Sample outcome

REQ-01 ALLOW · REQ-02 DENY (unmanaged BYOD, no MFA, 22:00) · REQ-03 STEP_UP then DENY (laptop health 65) · REQ-04 DENY (Alice's stolen creds from a Tor exit node) · REQ-05 STEP_UP then ALLOW with a 300 s token · all 5 PEP attacks blocked (expired, scope abuse, forged, revoked, no token). Challenge: 10 questions.

7. Lab 3 — Log Forensic Inspector & Hash Verifier

4.9 data sources2.4 indicators1.4 hashing File: labs/lab3_log_inspector.py · Data: sample_logs.json

Pipeline

  1. Parse raw lines <ISO8601> <host> <source> key=value key="quoted value" (shlex) into LogEvent. Sources: FW, WinEvt, HTTP, EDR. Malformed lines are counted as parse errors, not dropped silently.
  2. Enrich with an offline GeoIP table (geoip in the data file).
  3. Detect with correlation rules → Finding(rule, severity, summary, evidence_lines, mitre), sorted CRITICAL → LOW.
  4. Extract IOCs by regex: public vs RFC1918 IPs, SHA-256/SHA-1/MD5, user agents, domains.
  5. Verify integrity: a salted SHA-256 hash chain over the lines plus an HMAC-signed manifest.

Detection rules

FunctionRuleLogicMITRE
detect_brute_forceBRUTE_FORCE(_SUCCESS)≥5 × Event 4625 for one user+IP within 10 min; CRITICAL if a later 4624 comes from the same user+IPT1110.001
detect_password_sprayPASSWORD_SPRAYone IP with 4625s against ≥4 distinct accountsT1110.003
detect_impossible_travelIMPOSSIBLE_TRAVELconsecutive 4624s for one user: distance >500 km and speed >900 km/h (haversine)T1078
detect_port_scanPORT_SCANone source → ≥10 distinct destination ports on FWT1046
detect_threat_intelTI_MATCH_IP / _USER_AGENT / _FILE_HASHmatches the bad IPs, UA patterns (sqlmap, nikto…) and hashes in config—
detect_sqliSQL_INJECTIONregex on HTTP path (' OR 1=1, UNION SELECT, …)T1190
detect_log_clearingAUDIT_LOG_CLEAREDEvent ID 1102 / 104T1070.001
detect_time_gapsLOGGING_GAP>30 min of silence on hosts in continuous_log_hosts (DC01, FW01)T1562.002

To add a rule, write detect_x(events, cfg) -> list[Finding] and append it to ALL_RULES.

Integrity model

link[i]  = SHA256( salt || link[i-1] || canonical_json(line[i]) ),  link[-1] = "0"*64
manifest = {count, chain, head, signature = HMAC(manifest_hmac_key, canonical_json({count,chain,head}))}
verify_manifest() -> VALID | TAMPERED (edit / delete / insert, with first broken index) | MANIFEST_FORGED

Sample outcome

38 events, 1 malformed line, 14 findings (3 CRITICAL): jdoe brute-force success, EICAR malware hash, Security log cleared, password spray, Tulsa→Moscow impossible travel, port scan, SQLi and sqlmap/Nikto, TI IP matches, and a 50-minute DC01 logging gap. The integrity tests detect a deleted line, an edited IP, an injected line and a forged manifest. Challenge: 12 questions (identify the activity from raw lines; distractors exclude any rule that also fired on those same lines).

1.3 change management5.1 governance File: labs/lab4_change_management.py · Data: sample_rfcs.json

Engine API

class ChangeAdvisoryBoard(policy)
  dependents_of(system) -> set     # transitive "who depends on me" (blast radius)

                                             observations, blast_radius, generated_backout, rehearsal)

Review checks

9. Lab 5 — AI Agent Supervisor & Guardrail Governor

4.7 automation4.6 non-human PAM5.1 HITL File: labs/lab5_ai_agent_governor.py · Data: sample_agent_actions.json

Model

Agents never act on production directly. Every proposed AgentAction(id, agent_id, action, target, parameters, justification, cab_ticket, confidence, t) goes to the AgentGovernor, which returns ALLOW, REQUIRE_HUMAN_APPROVAL (HITL) or BLOCK. The strictest verdict among all violations wins.

class AgentGovernor(policy)
  evaluate(action) -> GovernorDecision(action_id, agent_id, verdict, violations[], final, reviewer)
  human_review(action_id, reviewer, approve, reason) -> GovernorDecision
       # only HITL items; reviewer must be in human_approvers; agents can't approve; BLOCK is never overridable
  release_quarantine(agent_id, reviewer)
  ledger_chain(salt) / verify_ledger(chain, salt)      # hash-chained decision ledger

Checks (in order)

CodeVerdictTrigger
AGENT_QUARANTINED / UNKNOWN_AGENTBLOCKkill switch engaged / unregistered identity ("shadow AI")
OUT_OF_SCOPE_ACTIONBLOCKaction not in the agent's allowed_actions
HALLUCINATED_ASSET / _PATCH / _TICKETBLOCKtarget not in asset_inventory (for apply_patch, restart_service, isolate_host, run_command); patch not in catalog; CAB ticket not approved
IMMUTABLE_RULEBLOCKfirewall rule id in immutable_firewall_rules ([0])
OVERLY_PERMISSIVE_RULEHITLsrc any + port any
SELF_ESCALATION / PRIV_GRANT_NO_CABBLOCKgranting to an agent identity / privileged role without an approved CAB ticket
PROTECTED_CONTROL / AUDIT_TAMPERINGBLOCKtouching mfa, edr, audit_logging, siem_forwarder, backup_job / deleting or modifying logs
DANGEROUS_COMMANDBLOCKregexes: rm -rf /, curl|sh, chmod 777, disabling Defender, …
PROMPT_INJECTIONBLOCK"ignore previous instructions", "developer mode", … in the justification
RATE_LIMITBLOCKmore than 5 actions per agent in 60 s
LOW_CONFIDENCE / CRITICAL_ASSET / HUMAN_REQUIRED_CLASS / NO_JUSTIFICATIONHITLconfidence < 0.80 / disruptive action on a tier-0 asset / action in always_hitl_actions (disable_account) / empty rationale

Quarantine: 3 BLOCKs puts the agent in quarantine (kill switch); only a human approver can release it.

Sample outcome

20 actions → 8 ALLOW · 2 HITL · 10 BLOCK. patch-bot-01 is quarantined after an invented server and patch, a curl | bash, and a restart storm. Human review: A09 approved; A04 rejected; an override of rule 0 refused; an agent approving itself refused; an unauthorised user refused. Editing the ledger after the fact is detected. Challenge: 20 questions.

10. Lab 6 — Risk Management Calculator & BIA

5.2 risk management File: labs/lab6_risk_management.py · Data: sample_risks.json

Formulas & API

sle(AV, EF) = AV × EF          ale(SLE, ARO) = SLE × ARO        availability(MTBF, MTTR) = MTBF / (MTBF + MTTR)
assess(risk, appetite_ale) -> RiskAssessment(sle, ale, likelihood, impact, options[], treatment, rationale, residual_ale)
check_bia(entry) -> BIAResult(rpo_ok, rto_ok, availability, availability_ok, issues)
band(value, bands) -> 1..5     ARO_BANDS ≤0.05/0.2/1/5 ; SLE_BANDS ≤$10k/$100k/$500k/$2M

Treatment logic

  1. ALE ≤ risk appetite ($10,000) → ACCEPT (the risk owner signs).
  2. Otherwise compute net annual benefit: MITIGATE = ALE − ALE_after − control cost; TRANSFER = ALE × coverage − premium; AVOID = ALE − cost of stopping (only if activity_optional).
  3. Choose the best positive option. If none is positive → EXCEPTION (leadership sign-off with an expiry date).

11. Lab 7 — Incident Response Runner & Chain of Custody

4.8 incident response4.9 File: labs/lab7_incident_response.py · Data: sample_incident.json

Model

A playbook is an ordered list of action ids from a catalog. Each action has a phase (preparation, detection, analysis, containment, eradication, recovery, lessons_learned) and may have evidence{source, host, volatility_rank 1–6, hashed}, destroys_up_to_rank, requires[] and anti_pattern. grade_playbook(name, playbook, catalog, incident_id) returns PlaybookGrade(score, grade, issues, custody, ledger, ledger_chain).

Issue codePenaltyTrigger
EVIDENCE_DESTROYED−20power-off/reimage destroys uncollected evidence; or collecting evidence already destroyed
CHAIN_OF_CUSTODY−15evidence acquired without a hash
MISSING_PREREQ−15e.g. reimage before image_disk and legal_hold
NO_CONTAINMENT−15no containment step at all
ORDER_OF_VOLATILITY−10more volatile evidence collected after less volatile (RFC 3227)
PHASE_ORDER−10eradication/recovery before containment; recovery before eradication; containment after recovery; anything after lessons learned
NO_LESSONS_LEARNED / ANTI_PATTERN / UNKNOWN_ACTION−10 / −10 / −5missing review / flagged bad practice / not in catalog

Grade: A ≥ 90, B ≥ 80, C ≥ 70, D ≥ 60, otherwise F. Volatility ranks: 1 registers/cache, 2 RAM/process/network state, 3 swap/temp, 4 disk, 5 remote logs, 6 archives/backups.

Sample outcome

Rookie: 0/100 (F): pulled the plug, copied files to a personal USB unhashed, reimaged with no disk image or legal hold, tried to capture RAM after power-off, disabled the account after recovery, no lessons learned. Expert: 100/100 (A): 5 evidence items hashed in volatility order and a 10-entry custody ledger; editing who collected EV-001 breaks the chain. Challenge: 16 questions (phase identification, what to collect first, grade the playbook).

17. Design decisions & known limitations

Decisions worth knowing

  • The "AI agent" in Lab 8 is deterministic (soc_agent_propose), so results are reproducible and testable. It is designed to be swapped for a real model; every guardrail still applies.
  • Agent pacing: Lab 8 spaces proposals 15 s apart. At 5 s, Lab 5's rate limiter blocked legitimate incident response. Lab 5 still demonstrates a runaway agent.
  • disable_account always requires a human (always_hitl_actions), however confident the agent is.
  • Rate limiting counts attempted actions, including blocked ones. This is a defensible choice; you could argue for counting only executed actions.
  • BLOCK is never overridable through human_review: a human must change policy, not approve an exception at runtime.
  • Key separation: the evidence-sealing key is separate from the Zero Trust token key.

Known limitations

  • Simulated environments only: no real AD, firewall, SIEM or EDR integration.
  • The log parser expects the lab's key=value format, not real EVTX/syslog/CEF.
  • The Lab 4 rehearsal models only a few state attributes (patches, config version, running, firewall lists, schema).
  • The sample scenarios are fixed. Challenge mode re-asks the same questions in a different order, so you can memorise the answers (a random scenario generator is on the roadmap).
  • CI runs twice per PR push (push + pull_request triggers). Harmless, and can be trimmed.
  • SY0-701 Domain 3 (architecture) and objectives 2.2, 2.3, 4.1–4.5, 5.3–5.6 are not yet covered.

18. How to extend (recipes)

18.1 Add a new lab

  1. Create labs/labN_topic.py following the contract (skeleton below).
  2. Put thresholds in a new section of config/default_policies.json; put the scenario in data/sample_topic.json.
  3. Register it in labs/__init__.py: import it and add N: (labN_topic, "sample_topic.json").
  4. Add engine tests in tests/. The parametrised demo and challenge tests cover it automatically: they need ≥5 valid questions and 100% on self-answer.
  5. Update README.md (labs table, data files, practice ideas).
"""Lab N — Title.  Security+ SY0-701 objectives: X.Y ...  Run: python main.py lab N"""
from __future__ import annotations
from dataclasses import dataclass, field

TITLE = "Lab N — Title"
OBJECTIVES = "SY0-701 X.Y Topic"

@dataclass
class Result:
    item_id: str
    verdict: str                       # use words in terminal_ui.STATUS_STYLES for colour
    reasons: list[str] = field(default_factory=list)

def evaluate(item: dict, cfg: dict) -> Result:
    """Pure decision logic: no printing, deterministic, returns reasons."""
    reasons = []
    if item["value"] > cfg["threshold"]:
        reasons.append(f"value {item['value']} > threshold {cfg['threshold']}")
    return Result(item["id"], "FAIL" if reasons else "PASS", reasons or ["within policy"])

INSIGHT = {"objective": "SY0-701 X.Y ...", "concepts": [...], "failure_modes": [...],
           "ai_governance": [...], "exam_tips": [...]}

def run_demo(ui, policies: dict, data: dict) -> dict:
    cfg = policies["topic"]
    results = [evaluate(i, cfg) for i in data["items"]]
    ui.section("Step 1 — Evaluate")
    ui.table("Results", ["ID", "Verdict", "Reasons"], [[r.item_id, r.verdict, "; ".join(r.reasons)] for r in results])
    ui.insight(INSIGHT)
    return {"fail": sum(r.verdict == "FAIL" for r in results)}

def build_challenges(policies: dict, data: dict) -> list:
    from utils.challenge import Question
    cfg = policies["topic"]
    return [Question(prompt=f"{i['id']}: PASS or FAIL?", context=str(i), choices=["PASS", "FAIL"],
                     answer=evaluate(i, cfg).verdict, explanation="; ".join(evaluate(i, cfg).reasons),
                     objective="X.Y") for i in data["items"]]
